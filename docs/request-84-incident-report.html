Request #84 Database Incident Report

Date: October 12, 2026
Status: Production Data Modified
Severity: High
⚠️ Production Database Warning

Restock request #84 was fulfilled against the production Supabase database during local development testing. This report documents what happened, what was modified, and safe next steps for the team.

Executive Summary

During local development and manual restock testing, Bayron's local backend fulfilled restock request #84. Investigation confirms the following:

✅ Confirmed Facts

  • Request #84 was fulfilled against the production database — the local .env file pointed to Supabase main (production)
  • No environment isolation — the app has no NODE_ENV switching logic; it uses whichever database is in .env
  • 5 tables were modified — changes were made atomically via stored procedure
  • Data appears legitimate — item "Ahmar", 100 units to a branch, central stock reduced to 0

🎯 Root Cause

The StockLink backend loads environment variables via dotenv.config() with no path option, meaning it always loads .env from the project root. There is no conditional logic to check NODE_ENV or switch between development and production databases. Running node server.js or calling the API directly uses whatever DATABASE_URL is in .env — in Bayron's case, production.

📊 Data Modified

  • Item: Ahmar (via restock_requests.item_id)
  • Quantity: 100 units
  • Branch: One branch received the stock (restock_requests.branch_id)
  • Central stock: Now shows 0 quantity for item Ahmar
  • Branch stock: Now shows 100 quantity for item Ahmar at target branch

Tables Modified by Request #84

The stored procedure sp_fulfill_restock_request performs these changes in a single atomic transaction:

# Table Operation What to Look For
1 restock_requests UPDATE status → 'fulfilled', fulfilled_at timestamp set, approved_by user_id set
2 central_stock UPDATE quantity decremented by requested amount (now 0 for Ahmar)
3 branch_stock UPDATE quantity incremented by requested amount (now 100), last_restocked_at timestamp
4 stock_movements INSERT New row: movement_type='adjustment', quantity=100, moved_by = admin user_id
5 audit_logs INSERT (auto) Triggered by branch_stock update — contains before/after JSON snapshots

📝 Stored Procedure Details

  • File: migrations/006_fix_sp_movement_type.sql
  • Signature: sp_fulfill_restock_request(p_request_id INTEGER, p_warehouse_id INTEGER, p_approved_by INTEGER)
  • Transaction: All 5 table changes happen atomically (all or nothing)
  • Concurrency: Uses row-level locks (FOR UPDATE) to prevent double-fulfillment

Reversal Procedure (If Needed)

⚠️ Use Only If Data is Invalid

This stored procedure reverses a restock fulfillment safely. Test it in a non-production environment before running it in production.

Create the Reversal Procedure

CREATE OR REPLACE PROCEDURE sp_reverse_restock_fulfillment(
    p_request_id INTEGER,
    p_reversed_by INTEGER
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_branch_id INTEGER;
    v_item_id INTEGER;
    v_qty INTEGER;
BEGIN
    -- Get the fulfillment details
    SELECT branch_id, item_id, requested_qty
    INTO v_branch_id, v_item_id, v_qty
    FROM restock_requests
    WHERE request_id = p_request_id
      AND status = 'fulfilled'
    FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Request % not found or not fulfilled', p_request_id;
    END IF;

    -- Reverse branch stock (decrement)
    UPDATE branch_stock
    SET quantity = quantity - v_qty
    WHERE branch_id = v_branch_id
      AND item_id = v_item_id;

    -- Reverse central stock (increment)
    UPDATE central_stock
    SET quantity = quantity + v_qty
    WHERE item_id = v_item_id;

    -- Insert corrective stock movement (negative quantity)
    INSERT INTO stock_movements (
        branch_id,
        item_id,
        moved_by,
        movement_type,
        quantity,
        moved_at
    )
    VALUES (
        v_branch_id,
        v_item_id,
        p_reversed_by,
        'adjustment',
        -v_qty,
        NOW()
    );

    -- Reset restock request to pending
    UPDATE restock_requests
    SET status = 'pending',
        fulfilled_at = NULL,
        approved_by = NULL
    WHERE request_id = p_request_id;

    RAISE NOTICE 'Request % reversed successfully', p_request_id;
END;
$$;

Execute the Reversal

Preventing Future Incidents

To prevent this from happening again, implement these safety guards:

1. Startup Database Warning

Add to index.js (after dotenv.config())

// After require('dotenv').config()
const dbUrl = new URL(process.env.DATABASE_URL);
console.log('🗄️  Database host:', dbUrl.hostname);

if (dbUrl.hostname.includes('your-production-project')) {
    console.warn('⚠️  WARNING: Connected to PRODUCTION database!');
    console.warn('⚠️  Destructive operations will affect live data.');
}

Effect: Developers see which database they're connected to every time the server starts.

2. Test Isolation Check

Create scripts/check-test-env.js

const fs = require('fs');
const path = require('path');

const envTestPath = path.join(__dirname, '../.env.test');

if (!fs.existsSync(envTestPath)) {
    console.error('❌ ERROR: .env.test file not found!');
    console.error('Tests require a separate test database.');
    console.error('Copy .env.test.example to .env.test and configure it.');
    process.exit(1);
}

console.log('✅ Test environment file found');

Add to package.json

"scripts": {
  "pretest": "node scripts/check-test-env.js",
  "test": "jest"
}

Effect: Tests fail immediately if .env.test is missing, preventing accidental test runs against production.

3. Environment Label Variable

Add to .env

DB_ENVIRONMENT=production

Add to .env.test

DB_ENVIRONMENT=test

Add validation in critical routes (e.g., fulfillment)

// In fulfillment route
if (process.env.DB_ENVIRONMENT === 'production') {

    console.log('⚠️  Production fulfillment:', {
        requestId,

        timestamp: new Date().toISOString()
    });

    // Optional: Require extra confirmation
    // if (!req.body.confirm_production) {
    //     return res.status(400).json({
    //         error: 'Production operation requires confirmation'
    //     });
    // }
}

Effect: Critical operations are aware of the environment and can add extra safeguards in production.
