📋 StockLink Defense Cheat Sheet

🎯 60-Second Pitch (Memorize This!)

The user signs in through the React client. Express looks up the username through Prisma, bcrypt compares the password with the stored hash, and the API issues an expiring JWT with the user's ID, role, and branch. Protected API routes verify that token and enforce role and branch scope. A branch request stores the authenticated branch. PostgreSQL triggers create low-stock requests and audit entries. When an admin fulfills a request, Express calls the parameterized stored procedure. PostgreSQL locks the pending request and central-stock row, checks quantity, moves stock, writes movement and audit records, and updates the request in one transaction. The browser only sees the API response; it never receives the database credential.

🔄 Restock Workflow (Key Demo)

  1. Low stock detected: Trigger fires when quantity < threshold
  2. Request created: Auto-insert into restock_requests (status='pending')
  3. Admin reviews: Sees pending requests in queue
  4. Fulfill action: Admin clicks fulfill, selects warehouse
  5. Procedure executes: sp_fulfill_restock_request(request_id, warehouse_id, user_id)
  6. Transaction locks: FOR UPDATE on request + central_stock rows
  7. Stock transfer: Warehouse↓ Branch↑ both updated atomically
  8. Movement logged: Insert into stock_movements
  9. Status updated: Request marked 'fulfilled'
  10. Audit captured: Triggers write before/after JSONB snapshots

🔐 Security Highlights

  • JWT auth: Bearer token with user_id, role, branch_id (8hr expiry)
  • Bcrypt passwords: Hashed, never plaintext
  • Role middleware: requireAuth, requireRole
  • Branch scoping: API uses req.user.branch_id from verified token
  • SQL injection protection: Prisma parameterized queries + tagged $executeRaw
  • No direct DB access: Browser → API → Prisma → PostgreSQL

Database Constraints

  • Quantity ≥ 0 (CHECK constraint)
  • Unique usernames
  • FK cascades on supplier deletion
  • FK restricts on active stock/requests
  • Composite keys (branch+item, warehouse+item)

🎤 Top 5 Expected Questions

1. Why a stored procedure for fulfillment?

Answer: Multi-row operation (check request, verify stock, decrement warehouse, increment branch, log movement, update status) must be atomic. PostgreSQL keeps it transactional and centralized. Locks prevent double-fulfillment and overselling.

2. How do you prevent SQL injection?

Answer: Prisma structured queries parameterize values. Stored procedure uses $executeRaw tagged template. Never concatenate user input into SQL. Show in index.js: await prisma.$executeRaw`CALL sp_fulfill_restock_request(...)`

3. Why triggers instead of API logging?

Answer: Trigger observes mutation at database boundary. Captures changes even if not from normal UI path. Writes old/new JSONB snapshots. Coupled to the same transaction.

4. How does branch scoping work?

Answer: JWT contains verified branch_id. API derives identity from req.user.branch_id, not from browser payload. Role middleware restricts admin-only actions. UI hiding is convenience, not security.

5. How do you test safely?

Answer: Separate disposable test database in .env.test. Setup guard rejects same-project URL. Tests clear and seed data. Never run Jest against production.

💡 What-If Scenarios

  • Delete item with stock? FK RESTRICT rejects it
  • Negative quantity? CHECK constraint blocks it
  • Fulfill twice? Procedure locks + checks status='pending'
  • Overfulfill? Procedure locks warehouse row, checks availability, raises error
  • Edit branch in payload? API uses JWT branch_id, not payload
